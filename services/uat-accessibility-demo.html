UAT and accessibility first pass sample

A compact example of how I would report a paid UAT, accessibility, or pre-launch website QA pass. The point is not a long test plan. It is a short decision-ready report a product team can act on.

UAT pass/fail matrix Accessibility blockers Pre-launch QA Developer-ready issue notes Sandbox / test data only

Example scope

Product area

One onboarding or checkout-adjacent workflow in a SaaS, marketplace, mobile app, or marketing website.

Time box

2-5 hours. Enough to find real blockers, not enough to pretend the whole product is certified.

Output

Pass/fail matrix, confirmed issues, unclear requirements, launch risks, and a short next-pass checklist.

UAT pass/fail matrix

Area Status Evidence note Next action
Account setup Pass Test user can complete the basic setup flow with dummy data. Keep this in the smoke checklist.
Required field validation Fail Empty state message appears after submit, but focus stays on the button instead of the first invalid field. Move focus to the first invalid field and expose the error to assistive tech.
Mobile layout Risk Primary action stays visible, but the secondary legal text wraps under the sticky footer on narrow screens. Retest at 360px and 390px after layout adjustment.
Confirmation page Pass Confirmation ID, timestamp, and next-step copy are present in the test environment. Add this page to regression coverage.

This sample uses invented data. It is only a format example.

Accessibility issue examples

Severity Issue Why it matters Suggested fix
High Icon-only action has no accessible name. Screen-reader users hear a generic button instead of the action. Add an accessible label that matches the visible intent.
Medium Error text is visually clear but not programmatically tied to the field. Users may miss the reason a form cannot proceed. Associate the field and error text, then retest keyboard flow.
Medium Focus order jumps from the plan selector to the footer link. Keyboard users can skip the confirmation action by accident. Review DOM order and custom focus handling.

Pre-launch checklist

  • Confirm one happy path and two edge paths before starting.
  • Use staging, sandbox, dummy data, or test accounts only.
  • Separate confirmed bugs from unclear requirements.
  • Rank issues by release impact, not by how long the report looks.
  • Leave the team with a small regression checklist for the next build.

Boundary

I do not need production secrets, real payment data, KYC data, bank data, wallet credentials, production cookies, private customer records, owner-dashboard access, or any off-platform payment method.

For marketplace clients, all communication, milestones, delivery, and payment should stay on the marketplace platform.
